## 2. Adjustable tolerance

**Done.** Changes from the plan below: the "about" tolerance is a Profile field (schema step 9,
`user_profiles.about_tolerance_pct`, next to *Warn at*) rather than a `targets.*` setting, so it reaches
every place the profile does (Today, the range days, the period summary, the demo) without new plumbing;
the per-meal alert also leaves out low treatments, which it did not do before (guidance already did);
alerts call an "about" target "today's target". The plan builder needed no change: it judges only
potassium, sodium and fluid. `tests/test_tolerance.py` covers the rules, the API and the demo twin.

The existing setting `guidance.carb_tolerance_g` (5–20 g, default 10; `app/settings_registry.py`)
is used by guidance but not by Today's per-meal carbohydrate alert or "about" targets.

* Today's per-meal carbohydrate alert ("Projected over") uses `carb_tolerance_g`: a 60.6 g planned
  dinner against a 60 g goal no longer shows "over" (`handbook/REVIEW.md` A4, v0.3.0 review L8).
* New setting `targets.about_tolerance_pct` (0–10 %, default 0 = today's behaviour) for "about"
  targets (protein, calories): within the tolerance they show "on target", not "over".
* Server rule in `app/nutrients.py`, twin in `js/engine/rules.js`, vectors, Settings UI row with a
  plain explanation, handbook `app/` page on targets and warnings. Hypoglycaemia treatment entries
  (`purpose = "hypo"`) stay excluded from carbohydrate alerts as today.

## 4. Multi-day "running high" warning for planned food

**Done.** As planned, with these details: the rule is `periods.pattern_alerts` (twin `js/mock/log.js`), carried
by `DaySummary.pattern_alerts` and each range day; only today and later days with planned entries; a nutrient
the plan adds none of is never warned about; the weekly average needs at least 3 logged days in the 7; past
plans never eaten do not count; a hemodialysis dialysis day itself is left to its own alert. Today shows the
warnings first in the planned block, the Plan week marks the day. Checks: `tests/test_running_high.py` (rule,
inputs, API, twin across all three kinds) and a real-server Chromium walk at 375 and 1280 px.

Today the app warns per day: planned plus eaten food for **that day** against that day's limit
("If you eat what's planned, potassium reaches 104 %..."), weekly averages appear only in summaries
of eaten food, and hemodialysis users get the interdialytic block. Nothing combines the **last few
days** with **what is planned**.

New rule (server `app/periods.py` or `app/guidance/insights.py`, twin in `js/engine/`):

* **Daily-limit nutrients (potassium, sodium, fluid):** if the nutrient was at or over its limit on
  at least 2 of the last 3 days (eaten totals) and today's or a planned day's projected total would
  also be over, show a stronger warning on Today and the Plan view, for example: "Potassium was over
  your limit on 2 of the last 3 days, and this plan goes over again (2,750 / 2,500 mg)." It names
  the planned foods that add the most, using the existing `sources()` helper.
* **Weekly-average nutrients (phosphorus, protein):** the 7-day average of eaten days plus planned
  days, compared with the target; warn when the plan would take the average over.
* **Hemodialysis:** use the interdialytic interval instead of "last 3 days" for potassium, sodium
  and fluid (the existing `interdialytic_interval`).
* No new clinical thresholds: it uses each person's own targets and the existing `warn_fraction`;
  the 2-of-3-days pattern is a display rule, marked "opinion, needs clinical review" in
  `handbook/REVIEW.md` like the other guidance rules. Carbohydrates are not included, and
  hypoglycaemia treatment is never warned against or blocked. The warning informs; it never
  stops a person from planning or logging.
* High potassium wording links to the handbook `eat/potassium` page; a blood potassium result over
  the K-5 alert keeps its existing banner.
* Tests and vectors for: 0/1/2/3 high days, planned day over and not over, unknown values (never
  counted as 0), hemodialysis interval, weekly average with planned days; docs and handbook.

## 6. Lab results from a CSV file

**Done**, with one change of design: there is no `POST /api/labs/import/preview`. The browser reads the file
(`js/engine/lab_import.js`) and shows the preview itself, and only the results the person ticks go to
`POST /api/labs/import` (test, value, unit and date). A patient-portal export can hold names, dates of birth
and record numbers, so the file never reaches the server. The reader has no Python twin; its vectors
(`tests/data/lab_import_vectors.json`, from `tests/js/gen_lab_import_vectors.mjs`, reviewed by hand) run in
`node tests/js/run_vectors.mjs`, and `tests/test_lab_import.py` checks their conversions against
`app/units.py`. The import route checks each item like `POST /api/labs`, skips repeats and lists what it
refused. Values the app cannot read as one number ("<0.5", ">90", "1,200") are left out with the reason
rather than guessed.

* `POST /api/labs/import/preview` (parse, never saves) and `POST /api/labs/import` (saves the rows
  the person confirmed); CSV with a date column and one column per analyte of `app/units.py`, unit
  from the header (`Potassium (mmol/L)`) or chosen per column.
* Limits: 1 MB, 1,000 rows; every value goes through the existing plausibility ranges and unit
  conversions; refused rows are listed with the reason; duplicates (same analyte, date, value) skipped.
* UI: Lab results → "Import from a spreadsheet", a preview table with checkboxes, then save.
* Demo twin, tests (good file, wrong units, implausible values, duplicates, other user's data
  untouched), docs and the handbook `app/labs` page.
