# Roadmap: work the specifications defer to a later version

One line per item, with the specification that defers it (the design notes are in
[`docs/dev/research/`](dev/research/)). Items leave this list when they ship (move them to
[CHANGELOG.md](../CHANGELOG.md)) or when the owner drops them. Each feature owner appends to its own
section. Last reviewed for the v0.3.0 release (2026-10-07).

## Accounts, sign-in and secrets (note 07)

* OIDC sign-in (Authelia, Authentik, Keycloak, Kanidm, Pocket ID), choosing between Authlib 1.8 + itsdangerous and the project's own PKCE code (a new runtime dependency needs a contract decision) — note 07 F7, §3.1 and §6 "Later (v0.4)".
* A second factor for local sign-in: one-time codes (TOTP, `pyotp`; the biggest security gain left for a password-only health app, 3–5M) and/or passkeys (WebAuthn, `webauthn` 3.0.1) as a second factor or passwordless; with a second factor the 8-character password minimum becomes acceptable — note 07 §3.1, §6 "Later (v0.4)" and §8 risk R3.
* Optional SMTP for self-service password resets (today an admin makes a reset link or uses `python -m app.admin reset-password`) — note 07 §6 "Later (v0.4)".
* Read-only sharing with a caregiver or dietitian (`shares(owner_user_id, grantee_user_id, scope, created_at, revoked_at)` and a `Principal(user, acting_for)` dependency) — note 07 §6 "Later (v0.4)".
* Let **Import from a file** take the export `.zip` itself (small): read `export.json` out of the archive in the browser (`DecompressionStream('deflate-raw')` over the zip's central directory, with the size checked while reading) so nobody has to open the archive first; today the page says to. Follows the import (`app/data_import.py`).
* An opt-in password pepper (`PASSWORD_PEPPER_FILE`) once operators keep their keys off the data volume — note 07 §3.2 ("not in v0.3 … revisit").
* One SQLite file per person (strongest isolation, deletion = removing a file) — note 07 §3.7 ("Revisit for v1.0").

## Ideas from the owner (no specification yet)

Added 2026-10-07 after comparing similar projects (for example Kidney Advisor, a browser-only CKD tracker on GitHub Pages that imports Apple Health blood pressure, lab CSVs and patient-portal C-CDA files). Each needs a design note in `docs/dev/research/` before it is built; sizes are rough.

* **A "keep my data in this browser" demo mode (medium).** **Done (2026-10-15)** ([`demo.md`](demo.md), [`CHANGELOG.md`](../CHANGELOG.md), [`ARCHITECTURE.md`](../ARCHITECTURE.md#keep-my-data-in-this-browser-demo-only)): the Pages demo's banner has **Keep my data in this browser**, a sheet that says plainly that the data stays only in this browser on this device, that nothing is sent anywhere, that clearing site data, private browsing or the browser freeing space can delete it, to export regularly, that a shared device shows it and that a real server is the way for real use; it is off until "I understand" is ticked, asks the browser to keep the data (`navigator.storage.persist()`) and shows the answer. The demo API's whole state is saved in IndexedDB after each write (debounced) and read back at the next start (a stored copy from a newer version is never loaded or overwritten; a second tab that finds the copy changed stops saving and says so), with **export** of `export.json` in the server's shape and **import** of it (a twin of `app/data_import.py` with the same refusals, checked by `tests/data/import_vectors.json`, which the real server generates) so data can move to a real server through the existing import. "Stop keeping data here" deletes the copy. The mode exists only in the demo build. Still open: a zip export in the demo (it gives the JSON only), and the demo's own "Import from a file" does not read the export `.zip` (neither does the server's page: see "Let **Import from a file** take the export `.zip` itself" above). The self-hosted server stays the full version.
* **Lab results from a patient-portal C-CDA file (medium).** **Done (2026-10-15)** ([`targets-and-labs.md`](targets-and-labs.md#in-the-app), [`CHANGELOG.md`](../CHANGELOG.md)): Labs → Import from a patient portal file (C-CDA .xml) reads the lab results of a portal's C-CDA "health summary" by LOINC code, with the same table, units and review-and-confirm step as the Apple Health import (new rows ticked, only ticked rows saved through `POST /api/labs/import`). **Decision: the XML is parsed in the browser, not on the server with `defusedxml`.** Least trust: the file holds the patient's name, address and ids, and parsing on the device uploads nothing, adds no runtime dependency (so no contract decision) and leaves the server with no XML parser to attack; the browser's `DOMParser` never loads an external entity or DTD, and a file with a `<!DOCTYPE` or `<!ENTITY` is refused before it is parsed (a real C-CDA has none). Limits: 20 files of 5 MB, 200,000 elements and 64 levels per file, 1,000 rows. It reads only Results sections (templateId `2.16.840.1.113883.10.20.22.2.3.1` and `…2.3`) and Result Observations (`…4.2`), cited in `targets-and-labs.md`. **Cost of the decision:** the CSP's `require-trusted-types-for 'script'` makes `DOMParser` a sink, so the CSP gained a second named Trusted Types policy, `kh-xml` (`trusted-types kh-sw kh-xml`), created in one file, accepting only strings without a DOCTYPE or ENTITY. **Not built / for the owner:** a run on real exports from at least two portals (the samples are hand-written; Chromium runs a sample through the real parser, but no real MyChart or other portal file has been tried: look at what the headline says a real file skips); the R2.1 definition page of the entries-optional template (`…2.3`) could not be fetched when this was written, so that OID rests on HL7's own example and a second source; results the portal puts only on the organizer's `effectiveTime` (the reader uses the observation's own); sending more than 1,000 rows in several requests.
* **Lab results from Apple Health clinical records (medium).** **Done (2026-10-15)** ([`targets-and-labs.md`](targets-and-labs.md#in-the-app), [`CHANGELOG.md`](../CHANGELOG.md)): Labs → Import from Apple Health (clinical records) reads the `clinical-records/` FHIR JSON files of the Health export **in the browser, on the device, with nothing uploaded**: `Observation`s (and Bundles of them) that are final, amended or corrected, matched by LOINC code (26 codes for the app's nine tests, each looked up in LOINC 2.82 and cited with its loinc.org page), converted only by the app's own unit table, shown in the CSV import's review table (new rows ticked) and saved through the same `POST /api/labs/import`. Up to 2,000 files of 1 MB each. **Not built / for the owner:** a run on a real Health export from an iPhone (the sample resources are hand-written; real exports may name tests with codes this table lacks, or units it refuses, and the summary line says how many, so look at what a real export skips and add a code only after the same LOINC lookup); the whole-blood, venous, arterial and race-specific eGFR codes are left out on purpose; reading `export.xml`'s `ClinicalRecord` entries instead of the folder (the folder is simpler and smaller); a "pick a folder" chooser (iOS Safari offers files only); sending more than 1,000 rows in several requests.
* **Weight (and later blood pressure) from an Apple Health export (medium).** An iPhone web app cannot read HealthKit directly, so: upload the `export.xml` from the export zip, parse it as a stream (the file can be hundreds of MB) and keep only body mass, and blood pressure once the app has a place to record it (a new table, Trends chart and handbook page). Glucose and insulin stay out: no dosing, and CGM apps keep their own alerts.
* **Live push from an iPhone Shortcut (medium).** A Shortcut (or a Health automation) that sends the latest weight or blood pressure to the person's own server. Needs per-person API tokens with a narrow write-only scope (the app has session sign-in only today), rate limits, and docs for the Shortcut.
* **Lab results from a PDF report (medium, needs AI).** Behind the optional AI (note 04), like label photos: the model proposes values, the person confirms each one, nothing is saved unconfirmed. **The photo version is done (2026-10-15)** ([`ai.md`](ai.md#lab-report-photos), [`CHANGELOG.md`](../CHANGELOG.md)): Labs → Read a lab report photo takes a photo or screenshot of a report (a PDF can be screenshotted), the AI copies the printed results of the app's nine tests, the app keeps only the tests, units and plausible values it knows (the checks of `POST /api/labs`, no future date) and counts what it dropped, and the rows come back **all unticked** for the person to check and save through the existing lab import. Because a report shows a name, a date of birth and record numbers that cannot be removed from an image, it runs **only on the local AI** (`ai.route.labs` is `local` or `off`; never a cloud AI, never a person's own provider), has its own consent purpose (`labs`, schema step 16) and keeps no content in the AI activity row. **Not built:** uploading the PDF itself (text extraction or page rendering on the server, then the same review); the owner's live run on a real local vision model (`scripts/ai_eval.py` skips the local-only cases; try real reports on the Arc A770 or a larger card and watch which units and dates the model misreads).
* **An assistant you can talk to (the owner's main AI wish; 2026-10-08).** Meal planning with kidney limits is hard, and harder when sick; the owner wants to say "I'm craving something sweet", "what fills in the rest of today", "make this recipe fit", or "I went low", and get suggestions, a projection for the day and recipes, by text or voice. Design decisions so far:
    * **Numbers never come from the model's memory.** The model may propose any food or recipe; the app resolves every item against a known source (built-in list → USDA FoodData Central, using its household-measure gram weights → Open Food Facts for brands) and recomputes totals, per serving for recipes, marking unknown potassium or phosphorus as unknown, never 0. Foods are saved to the person's list as a side effect of use, never as a prerequisite (the owner rejected "only foods already in the list" as too much friction).
    * **Lows and red flags stay rule-based**: "I went low" gets the Treating a low card first (`app.guidance.hypo.prefilter`), the chat helps afterwards; emergency wording gets Get help now. No doses, no medicine advice, no lab interpretation; dangerous ground ("salt substitute", NSAIDs, big protein or fluid changes) gets a plain warning and "confirm with your team".
    * **Recipes**: a recipe page's ingredient list (schema.org `Recipe` data, present on nearly every recipe site) or pasted ingredients → the same resolution → per-serving totals and warnings → saved as a saved meal with a link to the source. Site nutrition panels usually omit potassium and phosphorus, so the app recomputes every time; kidney-specific sites (Kidney Kitchen, DaVita, Kidney Community Kitchen) are the useful search targets. Recipe values are estimates (cooking losses, leaching), and the UI says so. Commercial recipe APIs (Edamam, Spoonacular) are optional later: keys, rate limits, terms that restrict storage.
    * **Two front doors, one back end.** Step 1, *an external chat front end* (3.5–5M): a per-person API token (sessions are cookie-only today), a "check this meal or recipe" endpoint that does the resolution above, exposed as an MCP server (the item in the Optional AI section) so the chat client is a free choice: Open WebUI (voice in and out, per-model system prompts, MCP tools; verify the version), a Hermes Agent profile *with* tools (this is the reverse of the app's `hermes` preset, which must stay tool-free: there the app calls Hermes as a model, here the assistant calls the app), or a vendor app over MCP (which would mean exposing the server to the internet: not recommended for health data). The frontier model's prompt makes it call the app for every number. Web fetching stays in the chat client; the app keeps talking only to USDA, Open Food Facts and its AI provider. The owner's intended stack (2026-10-08): Open WebUI for the screen and voice → a Hermes profile with tools as the agent, chosen for its persistent memory and self-written skills (what the person likes, what worked on sick days) → LiteLLM as the model router (keys, spend, local Ollama alias as fallback) → a frontier model. Rule for that memory: it holds preferences, routines and recipes that worked, never targets, lab values or totals, which are fetched from the app on every turn so a care-team change is never overridden by a remembered number. Step 2, *in-app chat* (the earlier "Ask about my own data" item, 5–10M): the same endpoints behind an "Ask" screen in the app, answers checked by the existing guard, and voice: a microphone button using a *transcription provider* setting (1–1.5M; the browser's own speech recognition was rejected on 2026-10-15: Chrome sends that audio to Google and Safari to Apple, outside the owner's control, and Firefox has none): one OpenAI-compatible `/v1/audio/transcriptions` endpoint, which is what both a local whisper.cpp or Speaches container (the app never runs Whisper itself, as it never runs Ollama) and cloud services (OpenAI, Groq, Deepgram) expose, so `STT_BASE_URL` + `STT_API_KEY_FILE` + `STT_MODEL` cover both, under the same SSRF policy and consent sheet as AI providers ("your recording is sent to …"); recordings are transcribed and discarded, never stored, and the transcript is shown before anything goes to a model. The same whisper.cpp container can serve Open WebUI's voice input for the external front end. The reply is read aloud with the browser's own voice (on-device). Honest limit: a prompt can ask a model to check its numbers; only the in-app route enforces it in code, so the Hermes step is for one informed person.
    * **Status (2026-10-14): step 1 is done: the MCP server, read-only, and saving for a token that is allowed to** ([assistant.md](assistant.md), plan `dev/plans/assistant-step1.md`): personal access tokens (part A, Settings → Assistant access) and `POST /mcp` (part B) with four read-only tools: `safety_check` (the Treating a low and Get help now cards, rule-based), `get_today` (Today's own numbers), `search_foods` (own foods, the built-in list, then USDA without saving) and `check_meal` (each item found in the app or asked about, scaled by servings, grams or the food's own household measure, the day projected as if planned; nothing saved). **Part C is done too (2026-10-14):** a token made with "Can also save food and recipes" has the scope `assistant:log` and two more tools, `log_food` (items placed exactly as `check_meal` places them, saved eaten or planned in one all-or-nothing step through the log API's own function, with `purpose: "hypo"` for food eaten to treat a low, answered with what was saved and the day's figures) and `save_recipe` (a saved meal holding the whole recipe, its note saying "Makes N servings" and keeping the source link as text); a USDA food named by its `fdc_id` is added to the person's list through the import code first (and `check_meal` can read one without saving it); every save is in the person's activity list with the token's name. **Step 2, part A is done (2026-10-15)** ([assistant.md](assistant.md#the-ask-screen-the-chat-inside-the-app), plan `dev/plans/assistant-step2.md`): the in-app **Ask** screen, a text chat behind the switch `ai.chat_enabled`: the rules answer a low or an emergency without a model call, the model works through a JSON step protocol (`get_today`, `search_foods`, `check_meal`, at most 6 tool calls, every call counted in the AI quota and gate), and the answer is checked in code before it is shown (text policy, dose check, number check, lab note, "From the app" figures); its own consent purpose `chat` (schema step 12), no transcript on the server. **Part C is done (2026-10-15)** ([assistant.md](assistant.md#the-ask-screen-the-chat-inside-the-app), plan `dev/plans/assistant-step2.md` "Part C"): the Ask chat can save, with a trust setting the owner asked for ("so I don't have to babysit it by confirming every response ... a toggle with a warning"): by default a card the person presses Save on (nothing written until then, through the normal routes), or, behind the admin switch `ai.allow_trusted_saves` and a warning sheet, "Trust it for this conversation" or "Trust it always", which save at once, all or nothing, with Undo on every save, a duplicate guard (`assistant_ask_keys`, schema step 13), and `via: "Ask"` in the activity list; every change of the choice is audited. **Part B, voice, is built too (2026-10-15)** ([assistant.md](assistant.md#talking-to-ask-voice), [ai.md](ai.md#voice-input-speech-to-text), plan `dev/plans/assistant-step2.md`): a microphone in the Ask input behind the switch `ai.voice_enabled` (off by default) and `STT_BASE_URL` + `STT_MODEL` + `STT_API_KEY_FILE`, one OpenAI-compatible `/v1/audio/transcriptions` endpoint under the **same SSRF policy** as AI providers (a LAN host only when `AI_PRIVATE_HOSTS` lists it); `POST /api/ai/transcribe` takes one clip (webm, ogg, mp4 or wav, content type and first bytes checked, at most 1.5 MiB and a minute), its own consent purpose `voice` ("Your recording is sent to <host> to turn it into text, then deleted. Nothing is kept."; schema step 14) and a daily limit; recordings are transcribed and discarded, never written to disk or the database or logged, only an activity row without content; **the transcript goes into the question box and the person presses Send**; the reply is read aloud only with a voice built into the device (`localService`); `Permissions-Policy` allows the microphone for the app's own origin only; and `deploy/compose.stt-whisper.yaml` is a hardened local overlay (an internal network with no route out, the digest to be verified by the deployer). The browser's own speech recognition is not used and a test keeps it out.
